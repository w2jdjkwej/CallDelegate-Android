## 2. 汇总口径

### 2.1 去重原则

项目中保存了大量调参、失败复现和优化对照批次。若把同一组 WAV 的每次运行都作为新样本累加，会人为放大样本量。因此本文采用以下规则：

1. 每个独立语料集只选一个最终或有代表性的完整批次进入跨场景总表；
2. Before → After 对照单独列出，不再次计入 196 条总样本；
3. 文本盲测、设备 ASR 文本回放、真机 WAV 和 JVM 单元测试分别报告；
4. 失败样本保留在分母中，不因缺少延迟、实体或意图字段而删除；
5. 跨场景 CER 使用 `Σ编辑距离 / Σ参考字符数`；跨场景延迟由 196 条 `samples.json` 按 nearest-rank 重新计算。

### 2.2 真机与运行模式

- 测试设备：小米 `2509FPN0BC`
- Android：16
- ABI：arm64-v8a
- 导出 RAM：11,544,526,848 bytes，约 10.75 GiB
- ASR：Vosk small-cn 0.22 / `vosk:0.3.75`
- TTS：AISHELL-3 VITS / `sherpa-onnx:1.13.2`
- 代表批次模式：`REAL_TIME`；较新批次采用 `PRODUCTION_LATENCY`

该设备不是 6～8 GB 中低端目标机，因此低内存设备上的 PSS、RTF、温升和持续稳定性仍为 `NOT_RUN`。

- 峰值 PSS：423161 KB → 371307 KB，但两组均为单次运行，PSS 差异只作观察，不作稳定结论。

- 旧设备记录：169/196 = 86.22%；
- 当前规则回放：189/196 = 96.43%；

该对比隔离了 ASR 文本输入，能说明规则 NLU 的变化；还需要重新执行全量真机批次，才能证明联合链路的最终收益。

- 场景 23/24 = **95.83%**；
- 严格通过 20/24 = **83.33%**；
- 响应 P50/P95 = **2536/3124 ms**。

因此旧汇总中的前三项暂标记为“待找到对应 Run ID”，不能与该原始批次混写。当前代表性配送批次已经更新为第 3 节中的 24 条 `PRODUCTION_LATENCY` 结果：CER 9.93%、场景 23/24、严格通过 20/24、响应 P50/P95 520/956 ms。

## 12. 简历建议

可以优先使用有固定语料和 Before → After 证据的表述：

> 基于 Vosk、规则 NLU/NLG 与 sherpa-onnx VITS 构建 Android 端侧离线通话代接链路；在固定 36 条真机骚扰风险语料上，将端点宽限窗由 500 ms 优化至 300 ms，在 CER 2.67%、场景命中 34/36 不变的情况下，将响应 P50/P95 从 1001/1405 ms 降至 818/1216 ms。

也可以描述测试工程能力：

> 建立文本盲测、固定 ASR 文本 NLU 回放、真机 WAV 和 JVM 回归四层验证体系；公开源码快照重新执行 548 项 JVM 用例，0 failure、0 error、1 skipped，并对 6 场景 196 条代表性真机样本保留 CER、场景、严格失败、分阶段延迟和 PSS 证据。

不建议写成：

- “整体 NLU 准确率 97.22%”——该值只对应文本 blind v4 的 180 条业务场景；
- “端到端成功率 64.80%”——不同清单的实体契约不统一；
- “支持 6 GB 中低端手机稳定运行”——目标设备测试尚未执行；
- “196 轮连续运行无崩溃”——196 条来自多个独立批次；
- “真实电话对端稳定听到 AI”——本地音频写入不等于运营商链路对端可闻，相关限制见 [LIMITATIONS.md](LIMITATIONS.md)。
